# 🧠 SYSTEM CONTEXT: Инструкция ИИ по работе с `project_map.md`

Этот файл — рабочая инструкция для ИИ (не для человека), которая описывает формат данных ментальной карты, как его читает и пишет `MindManager.java` (`DataLayer.fromMarkdown` / `toMarkdown`).

**Главный принцип:** ИИ обычно правит `project_map.md` точечно — текстовым патчем, без запуска Java. Значит текст, который ИИ пишет руками, обязан быть на 100% совместим с `fromMarkdown()`, иначе при следующей загрузке карта развалится или потеряет данные молча (без ошибки).

---

## 📍 Точные URI файлов ментальной карты

* **Структура и топология карты (источник истины):** `file://~plugin/project_map.md`
* **Конфигурация Канбана и колонок:** `file://~plugin/map_config.json`
* **Состояние представления (свёрнутость веток, направление):** `file://~user/config/crazy_german/map_<rootGuid>.json`
* **Детализация отдельных задач:** `file://~plugin/tasks/task.[GUID].md`

## 1. Синтаксис узла

Каждый узел — это markdown-заголовок первого уровня, за которым может следовать свободный текст заметки, а затем список атрибутов:

```markdown
# Название узла
Свободный текст заметки (опционально, одна или несколько строк)
- id: 4ea17104-4c78-461f-b880-4134bf91f3ca
- parentid: 318d86a7-834c-4348-a578-755b5124e98d
- type: module

```

Правила:

* Заголовок — всегда `# ` (ровно одна решётка + пробел). Уровень заголовка не несёт смысловой нагрузки — это не глубина дерева, все узлы карты используют один и тот же уровень `#`.
* Сразу под заголовком может идти произвольный текст заметки — одна или несколько строк, не начинающихся с `- `. Он целиком уходит в поле `data.note` узла (об этом подробнее в §2).
* После заметки (или сразу после заголовка, если заметки нет) — построчный список атрибутов вида `- key: value`, по одному на строку, без вложенности через отступы.
* **Порядок атрибутов: `id` пишется первой строкой списка атрибутов**, сразу за ней (если есть) `parentid`, затем `isroot` (только у корня), и только после них — остальные поля (`type` и т.д.). Придерживайтесь этого порядка при ручном редактировании — так его генерирует сам `toMarkdown()`, и это держит дифф минимальным и предсказуемым.
* Разбор строки атрибута идёт по первому символу `:` в строке — всё слева от него (после `- `) это `key`, всё справа (обрезанное по пробелам) — `value`. В имени ключа не должно быть `:`, а вот значение может свободно содержать двоеточия (JSON-объекты вида `{"start":"..."}` парсятся нормально).
* Три ключа зарезервированы и кладутся в корень узла: **`id`**, **`parentid`**, **`isroot`**. Всё остальное (`type`, `dates`, `kanbans`, `path`, `note` и что угодно ещё) уходит во вложенный объект `data`.
* Пустая строка между узлами — рекомендуемая практика для читаемости и чистых диффов, но не обязательна: парсер игнорирует пустые строки.
* Топик (текст после `# `) не должен начинаться с `- `.

### Форматирование значений атрибутов

* `true` / `false` (без кавычек, любой регистр) → булево значение.
* Строка, начинающаяся с `{` и заканчивающаяся на `}`, или начинающаяся с `[` и заканчивающаяся на `]` → парсится как JSON (объект/массив). Пишите его в компактном однострочном виде.
* Всё остальное → сохраняется как обычная строка "как есть", без кавычек.

Пример строки с вложенным JSON:
```
- dates: {"start":"2026-06-28T09:00:00Z","end":"2026-07-02T18:00:00Z"}
- kanbans: [{"code":"workflow","value":"done"},{"code":"priority","value":"high"}]
```

## 2. Поле `note` — особый случай

`note` — единственное поле `data`, которое в markdown не пишется как `- note: ...`, а хранится как свободный текст сразу под заголовком узла:

```markdown
# Задача
Подробное описание задачи
- id: 8adda0e2-46c2-4a73-abd5-61aeab81d123
- parentid: 4ea17104-4c78-461f-b880-4134bf91f3ca
- type: task
```

* Любые строки после заголовка, которые не начинаются с `- ` и не пустые, склеиваются построчно (через перевод строки) в `data.note`.
* Держите заметку короткой (не более пары строк) — это короткая пометка, а не место для длинного текста; для развёрнутого описания задачи используйте `~plugin/tasks/task.[GUID].md`.
* При записи узла не добавляйте отдельную строку `- note: ...` — если так сделать, значение всё равно попадёт в `data.note`, но при следующей генерации файла кодом оно будет переписано в формат свободного текста под заголовком. Чтобы не создавать лишний дифф, сразу пишите заметку как свободный текст.

## 3. Иерархия

Дерево строится исключительно по полю `parentid`:

1. Ровно один узел с `isroot: true`, и у него нет `parentid` — это корень дерева, соответствует проекту.
2. У всех остальных узлов обязателен `parentid`, указывающий на `id` существующего в файле узла-родителя.
3. Узел без `parentid` и без `isroot: true` — "осиротевший" узел; фронтенд (jsMind) строит дерево от единственного корня, и такой узел не отобразится корректно. Никогда не оставляйте узел без `parentid`, если это не корень.
4. Если `isroot: true` стоит у нескольких узлов — при сохранении их `data` будет по очереди слито в `map_config.json` (последний перезапишет предыдущий), а для файла состояния будет использован id последнего встреченного узла с `isroot: true`. Держите ровно один `isroot`.
5. Порядок узлов в файле не имеет структурного значения — парсер читает их как плоский список независимо от взаимного расположения родителя и детей. Для читаемости и диффов рекомендуется располагать детей рядом с родителем, но это не требование парсера.

## 4. Схема данных узла (после разбора в JSON)

```json
{
  "id": "string(GUID)",
  "parentid": "string(GUID)",
  "isroot": true,
  "topic": "string",

  "data": {
    "type": "root|module|group|milestone|idea|note|document|task|default",
    "note": "короткая заметка (опционально)",
    "...": "остальные поля зависят от type, см. §5"
  }
}
```

* **`id` нельзя терять при редактировании существующего узла.** Потеря `id` → узел останется без идентификатора (парсер не генерирует новый GUID сам), что разорвёт связь с `task.[GUID].md` и с view-state файлом.
* Для нового узла — генерировать новый GUID (v4), не переиспользовать чужой.
* **`isroot`** ставится только у корня, и только у корня отсутствует `parentid`. При сохранении Java сам вычищает из корневого узла всё содержимое `data`, кроме `type`, и переносит остальное (например `kanban_settings`) в `map_config.json` — поэтому в `project_map.md` у корня `data` должен быть минимальным: только `type: root`.
* Никогда не пишите `expanded` / `direction` как атрибуты узла — это слой пользовательского view-state, Java вырезает эти ключи из данных узла на верхнем уровне при сохранении; в `project_map.md` им не место.
* Не кладите в `data` тяжёлые вещи — лог времени, список изменённых файлов, историю диалога. Это уровень задачи, живёт в `.german/tasks/task.[GUID].md`; в карте — только факт существования узла-задачи и его лёгкие поля.

## 5. Типы узлов (`data.type`)


`type` — свободная строка, парсер её не валидирует. Ниже — типы, для которых на фронтенде есть отдельные `NodeViewFactory`-классы (`RootNodeView`, `ModuleNodeView`, `GroupNodeView`, `MilestoneNodeView`, `IdeaNodeView`, `NoteNodeView`, `DocumentNodeView`, `TaskNodeView`), плюс `default`/произвольный тип падает на `BaseNodeView`.

| type | Назначение | Типичные поля |
|---|---|---|
| `root` | Единственный корень дерева | только `type` (остальное — в `map_config.json`) |
| `module` | Крупный модуль/подсистема проекта | опционально `sys` — короткий код подсистемы для бейджа; опционально `note` |
| `group` | Логическая группа/контейнер для объединения узлов | опционально `note` |
| `milestone` | Контрольная точка (веха) проекта или этапа | опционально `dates`, `note` |
| `idea` | Мысль/направление, ещё не оформленное в задачу | обычно только `type`, опционально `note` |
| `note` | Текстовая заметка внутри карты | `note` — сам текст заметки (свободный текст под заголовком, см. §2) |
| `document` | Ссылка/привязка к документу проекта | `path` или `ref` |
| `task` | Задача, отображается как канбан-карточка | `dates`: `{"start":"ISO8601","end":"ISO8601"}` (полный datetime с временем и `Z`); `kanbans`: массив `{"code":"...", "value":"..."}` — по одной записи на каждый список канбана из `map_config.json → kanban_settings.lists`; опционально `note`; опционально `bx` — id связанной задачи в Битрикс24 |
| `default` / любой другой | Обычный узел без специфического поведения | опционально `note` |

У задачи статус/приоритет хранятся не отдельными полями, а единым массивом `kanbans`, где каждый элемент ссылается по `code` на список из `kanban_settings.lists` (`workflow`, `priority`, ...) и несёт своё `value`. Перед простановкой `value` сверяйтесь с актуальным `map_config.json → kanban_settings.lists[].options[].value`.

## 6. Точечные операции — как редактировать без поломок

**Добавить узел:**
1. Сгенерировать GUID.
2. Дописать блок: `# Topic`, при необходимости строка(и) заметки, затем `- id: ...`, `- parentid: <id родителя>`, прочие `- key: value` — в любое место файла (для читаемости — рядом с родителем/сиблингами).

**Переместить узел:** изменить только его строку `- parentid: ...` на id нового родителя.

**Переименовать:** менять только текст после `# `.

**Изменить заметку:** менять только текст свободной строки под заголовком (не трогая атрибуты).

**Изменить данные:** менять/добавлять/удалять только строки `- key: value` (кроме `id`), `id` не трогать.

**Удалить узел:**
- вместе с поддеревом — найти все узлы, у которых `parentid` рекурсивно ведёт к удаляемому, и удалить их блоки вместе с ним;
- с сохранением детей (re-parent на дедушку) — удалить только блок самого узла, а у всех узлов, где `parentid` указывал на него, заменить `parentid` на нужный новый (например, на `parentid` удаляемого узла).

**Всегда после правки — мысленно проверять:**
- ровно один узел с `isroot: true`, и у него нет `parentid`;
- у всех остальных узлов есть `parentid`, указывающий на реально существующий в файле `id`;
- у каждого узла есть `id`, и он идёт первой строкой среди атрибутов;
- у корня `data` минимален (только `type: root`).

## 7. Что этот файл не описывает

Слой представления (`map_<rootGuid>.json`) и слой задач (`.german/tasks/task.[GUID].md`) — отдельные форматы, ИИ не должен пытаться реконструировать их из `project_map.md`; это разные файлы с разной ответственностью (см. §1 общей архитектуры в `PROJECT.md`).
